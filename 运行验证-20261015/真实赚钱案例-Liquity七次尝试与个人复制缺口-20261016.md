# 一个真实正净案例：Liquity七次清算尝试

当前判断日期：2026-10-16。只做公开研究、已有原件静态审阅与算术；没有运行模型、回测、策略、EVM或交易。

**先承认已经证实的事实：一个普通调用地址在七次清算尝试中，一次成功、六次失败，扣除这七次全部实际网络费后，ETH/WETH数量净增加0.039100539874301130。**这是一段真实的协议服务收入原账，不是模拟结果。

同时明确没有证实的层级：公开的是协议的资格与报酬规则；该账户选择哪些机会、何时发送及如何竞价的完整事前规则仍未取得。因而它是已确认的历史正净服务案例，**尚不是完整事前锁定、个人照搬即可赚钱的策略案例**。没有据此计算年化、美元ROI或容量。

## 1. 修正此前的门槛混用

此前把“完整可持续复制系统未证实”多次汇总成“没有合格历史案例”，其中混入了并非确认一个限定历史账期所必需的条件：整个经营实体的终身/跨账户流水、完整私人bot、连续年度盈利及未来持续盈利。现纠正为分别核验四层：

| 要回答的问题 | 本例结论 |
|---|---|
| 这笔服务为何会收到报酬 | 公开协议规则及真实付款可对应 |
| 限定七次尝试，含失败网络费后是否为正 | 是，已核的ETH/WETH数量正增 |
| 完整机会选择/发送策略是否事前公开并可照搬 | 未证实；协议接口公开不能替代这层 |
| 你以后能否稳定获利、能放大到多大 | 未证实；不能从历史正数推出 |

账期仍须完整，不能只挑成功交易。若发现其他地址或链下活动实际承担这七次的成本，应归入相应经济损益；没有证据时不能虚构该项为零，也不能要求先查清整个实体的一切业务才承认可观察的资产净变化。本报告没有降低原本的“事前规则＋完整记录”标准来宣称全策略通过。

## 2. 谁需要这项服务，钱从哪里来

Liquity的借款人抵押资产借出BOLD稳定币；抵押不足时，协议需要清算仓位以处理风险。普通执行者提交仓位，公开合约验证并处理，成功后领取补偿。固定补偿由借款人预存储备支付，可变部分来自抵押物。本例债务由稳定池抵销，**执行者没有自己拿出3,004 BOLD替借款人还债**。

机制来源：[官方借款与清算说明](https://docs.liquity.org/faq/borrowing)，本轮2026-10-16再读。历史执行采用下列固定版本及真实收据，不把当前网页所有分支规则倒填给旧交易。

这项收入依赖“找到尚可处理的公开风险状态，并及时完成服务”。它不要求先预测未来股票价格，也不是XTX私人定价模型的复制品。与XTX可类比的仅是信息、风险处理、执行与成本控制这一组经济问题。

## 3. 规则先于结果，原件怎么对应

[2025-05-19官方上线公告](https://www.liquity.org/blog/liquity-v2-is-live)链接公开文档与代码，早于2026年本例。审计Final Version及历史代码为`abe7cbfbd465fba3812282c51773455766a70e96`；实际目标的浏览器验证源中TroveManager、Constants与该版逐字节一致。部署创建交易也早于本例。公开接口`batchLiquidateTroves`无清算者白名单；资格不满足会回滚，失败仍产生网络费。

[固定TroveManager源码](https://github.com/liquity/bold/blob/abe7cbfbd465fba3812282c51773455766a70e96/contracts/src/TroveManager.sol)。版本、源文本比对和部署原件见既有`evidence/direct-protocol-case-20261016/`，本轮核这些已存原件的指纹与独立审阅，没有重新编译或执行。

这支持协议机制早于结果已公开披露；精确首次公开时刻缺历史网页存档，目标字节码验证依赖浏览器Exact Match声明，不称独立编译验收。私人选单和发单策略的事前公开性另列未知。

## 4. 七次真实尝试：成功和失败一并纳费

调用地址：`0x000000000004Fbf65B56ae13b507556c2C06bFf5`。存档地址页列全部8条普通交易：一条0.5 ETH资金转入，随后七条清算尝试，发送序号nonce0—6连续。以下不是教学示例。

| UTC日期/时间 | 结果 | 收到WETH | 实付网络费ETH |
|---|---|---:|---:|
| 2026-06-03 20:56:59 | 失败 | 0 | 0.000090712853669174 |
| 2026-06-04 02:11:11 | 失败 | 0 | 0.000294509819669186 |
| 2026-06-05 06:24:59 | 成功 | 0.0475 | 0.005213757965143884 |
| 2026-06-05 06:26:35 | 另一抵押物分支失败 | 0 | 0.002127313628530002 |
| 2026-06-05 13:58:47 | 失败 | 0 | 0.000220910677688402 |
| 2026-06-05 19:02:23 | 失败 | 0 | 0.000344542401934248 |
| 2026-06-06 04:39:47 | 失败 | 0 | 0.000107712779063974 |
| **合计** | **1成功、6失败** | **0.0475** | **0.008399460125698870** |

故本范围的数量净增为：

`0.0475 − 0.008399460125698870 = 0.039100539874301130 ETH-equivalent`

ETH-equivalent表示按1 WETH对应1 ETH比较代币数量。WETH是封装的ETH；本例尚未解包/卖出，后续操作若发生还会有成本。不是美元到账利润，不是对不同日期ETH美元价值变化的估计。

原件：[全部普通交易与持仓地址页](https://etherscan.io/address/0x000000000004Fbf65B56ae13b507556c2C06bFf5)、[成功交易](https://etherscan.io/tx/0x2f7f282bae9388e4b4f3ebf36d09725a39eb221efe59445bbea7b2a73e35d4c3)、[容易漏计的另一分支失败](https://etherscan.io/tx/0x84370d2feba412d0463aebde303f276e2e5845b0c2830abd4ea04f95bc623560)。其余每条完整hash、交易费与原HTML指纹均在`root/june-caller-wallet-ledger-derived.json`及对应`direct-tx-originals/`。

本研究是从已发生的成功交易回溯选择账户，有选样偏差。纳入该账户全部七次普通发送的失败费，能纠正只看赢家单笔的高估，仍不能证明所有执行者平均赚钱，不能把1/7当未来成功概率。协议公开早于交易也不等于本研究已事先登记并完成样本外检验。

## 5. 本金和持仓也能对上

| 观察到的资产数量 | ETH/WETH |
|---|---:|
| 外部转入本金 | 0.5 ETH |
| 扣七次网络费后ETH | 0.491600539874301130 ETH |
| 清算收到WETH | 0.0475 WETH |
| 两种资产数量合计减外部本金 | +0.039100539874301130 ETH-equivalent |

成功前后State另确认ETH减少正好等于本笔实际gas，WETH从0增加至0.0475；[成功状态原件](https://etherscan.io/tx/0x2f7f282bae9388e4b4f3ebf36d09725a39eb221efe59445bbea7b2a73e35d4c3#statechange)。每笔费用使用实际gasUsed×实际gasPrice，已含优先费，不重复扣。

这闭合了所观察地址的普通交易及ETH/WETH数量账。没有把其他KONG代币计入收入，没有把0.5 ETH入金算利润，也没有把稳定池收到的抵押物算给执行者。资金发送方付的网络费已另存，不能自动算成本钱包支出；交易所提币费及实际归属未知。内部活动、链下节点/服务器、关联地址承担的服务成本未全面取得，因此不称全经营实体利润或个人全成本收益。

## 6. 这份钱容易复制吗

已确认的五次WETH失败，指向的仓位在该交易执行前已被他人清算；第六次另一分支未作同仓位配对。不能从区块纳入时间推断程序何时发现/广播。

另一个成功竞争者收到相同0.0475 WETH，却在解包后直接支付0.045585735056956094 ETH给区块收款方，再扣gas后From只增加0.001486561501712810 ETH。[该交易](https://etherscan.io/tx/0xb4c3c4ac35cbb7298d228d3c8954a8d4285ffb7076d33a01519f29c9850b5473)。这是不同地址的一笔，不混入七次账期，也不把单笔当经营利润。

由这些事实支持的机制判断是：**规则公开不代表报酬归你；及时识别、成交竞争与费用控制决定最后能留下多少。**不能用更大本金或更强聊天模型自动解决。

个人最值得低成本借鉴的一个环节，是**交易前资格与总成本核验**：确认仓位还有效、偿付/补偿路径与版本一致、报酬是否足以覆盖执行和失败成本。原规则及字段可公开研究，无须先找银行客户或训练模型。但本轮没有证明用普通电脑和免费数据能及时抓到足够机会，更没有证明你发单后也能保留该净增量。

## 7. 放大与财富目标还缺什么

收入随可成功处理的机会变化，不按账户余额机械同比增加。要讨论容量，至少需要连续机会总量、可捕获份额、竞争费用及扩大后的运行成本。本例七次尝试和另见九笔成功记录都不能推出全市场收入上限、稳定年收入或Gerko财富的1%。

唯一优先验证的问题是：**固定公开的资格与成本规则，能否在机会失效前识别出竞争后仍有正净报酬的事件？**完整私人系统不是确认本历史净增的前提，但该项未来个人能力不能由历史账替代。只读原件研究可继续核其输入、时序与成本边界；实际个人执行优势仍需另获授权并用事前固定方案验证。本轮不开发、不运行模型、不回测、不交易。

核心代码历史许可为BUSL，不能把研究阅读和任意复制部署等同。调用已部署接口与复制部署核心代码不同；个人未来具体适用条件仍需在那一步核清。这里只承认可研究环节，没有授予或假定生产使用许可。

## 8. 证据与当前取舍

当前优先保留这组**历史协议服务正净原账**，停止用“必须先证明未来持续盈利”推翻它；同时保持“完整事前选单策略尚未证实”。Uniswap只有建仓的样本仍不准入完整净账，Flashbots示例代码也没有被当成真实净盈利收据。研究状态未知不等于实测失败；原Kronos FAILED和封存预测均未改。

原件取得UTC及SHA256在既有direct-protocol-case与liquity-reproducibility证据目录；本轮新核验、范围审阅与收口记录在`evidence/complete-ledger-case-20261016/scope-audit/`。来源为公开原件，既有独立审阅分开检查源码身份、资金/费用及竞争配对。同一explorer的多页面互证不冒称独立节点证明。
