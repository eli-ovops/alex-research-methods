# 六月七笔费用补查：保留原正数量事实，未发现新增漏扣证据

结论：十月发现的额外付款，不能套到六月另一笔交易。固定六月七笔尝试的旧正数量事实仍有原件支持；本轮未找到需要补扣的新付款。它仍不是完整经营净利润，更不是我们可复制的未来收益。本轮不重算旧金额、不运行模型或回测、不交易。

## 2. 为什么没有直接补扣“区块费用接收方付款”

原成功交易的State页面显示，调用地址与奖励接收地址相同，其ETH减少量为 `0.005213757965143884`，与同笔原网页的网络手续费字段一致；WETH增量对应0.0475奖励。这里有同地址实际净变化的证据，不能因为缺少完整内部流，就再扣一笔假设的付款。

原State也显示区块生产方地址ETH增加，但该增加本身不能证明另有直接付款。网络手续费本来就可能向区块费用接收方分配，不能把这种State增加再次作为gas之外的费用。

原交易HTML仅提示“26 zero value Internal Transactions”，没有展开完整内部调用表，旧抽取也明确标记“未见不等于不存在”。因此本轮在读取新结果前，固定只查上述精确交易的公开内部转账索引一次：

- 来源：`https://api.routescan.io/v2/network/mainnet/evm/1/etherscan/api?module=account&action=txlistinternal&txhash=0x2f7f282bae9388e4b4f3ebf36d09725a39eb221efe59445bbea7b2a73e35d4c3`
- 读取：UTC 2026-10-19 22:52:53.573073—22:52:54.770235。
- HTTP 200，原体60字节：`status=0`、`message="No transactions found"`、`result=[]`。这次是明确的空索引结果，没有把通用错误或`NOTOK`当零。
- 含义：本索引没有提供额外原生币付款记录。它不认证完整trace，也不能证明所有内部支付绝对为零。因没有返回事件行，不能从中补出区块哈希或更强身份字段。

不重取既有HTML/State，不追加区块头，不查询钱包新历史。十月0.044625 ETH的实际付款仍属十月那笔交易；不能按其比例替六月补造费用。

## 3. 这对赚钱机制说明了什么

这组账支持一个有限但真实的历史事实：一次协议清算服务收到奖励，扣除该地址七笔尝试的已观察网络手续费后，仍有正的ETH/WETH数量增量。六笔失败的`NothingToLiquidate()`错误和手续费也保留，没有只展示赢家。

它没有说明这位执行者事前如何筛选任务、为什么六次执行时已无可清算任务、未来我们能取得多少任务，也没有证明其地址之外或链下的成本为零。不能用一成功六失败估计长期胜率。调用者、程序所有者和个人最终受益者的关系仍不能凭地址推定。

本轮未证实的新漏扣与尚未覆盖的成本必须分开：独立完整内部流、其他地址或链下付款、服务器与维护劳动、资金成本、入金及后续兑换费用和税务等仍不完整；不能把UNKNOWN补成0。这些缺口限制“完整净利润”表述，但不抹去原账户范围的正历史事实。

## 4. 收敛决定

**结束这项具体漏扣疑点的补查，保留六月正数量事实。** 没有新原件矛盾，不再反复查相同gas、State或空索引，也不以取得私有执行代码作为继续理解公开协议机制的前提。

目前能借鉴的是：把奖励、失败尝试、网络费、额外支付和最终净变化分开记录。个人能否持续取得任务、完整扣费后赚钱、扩大到多少资金，尚无通过证据。本轮没有使“接近Gerko财富1%”成为可验证的资金路径，不启动开发、实盘或新的收益实验。
