* A locked sequence run compares its reconstruction against a published contract

fx_pairs' holdout refused with "locked sequence fitted state does not reproduce
published predictions" while every value matched to the bit. The comparison in
`validate_locked_run` puts a prediction set that has been published against one
reconstructed from the checkpoint files, and the two carry the decision time in
different dtypes: publishing relabels a naive column as UTC through
`registry.store._timestamps_as_utc` and the parquet round-trip carries
microseconds, so the published side is Datetime(us, "UTC") while the
reconstruction is still Datetime(ns, None). `DataFrame.equals` compares dtypes,
so it reported a difference between two frames holding the same instants, the
same 9,960 rows and the same values.

Measured on fx_pairs training c3e8f312c25f (tcn, epoch 35): reconstructing twice
gives byte-identical frames, and both differ from the published set only in the
timestamp dtype.

It bites where a case study's sequence predictions arrive naive - fx_pairs, whose
dates come from a numpy datetime64 axis through `flush_fold_predictions`. The
other six carry them aware already, which is why the same validator passed on
every holdout before this one.

`align_keys_to_published` casts the key columns to the published dtypes before
the comparison, which relabels rather than converting and so cannot move a
decision time. It is the same move the surrounding code already makes for the
entity column, whose reader-facing name is renamed to `symbol` before comparing.
Value columns are deliberately left alone: they are compared with `np.allclose`,
which spans f32 and f64 on its own, and casting them would hide a real numeric
difference behind a widening.

* The outputs digest counted a cell the committed notebook never has

Every parameterized production run reported OUTPUTS CHANGED on a notebook nothing
had edited. `nb-run.sh` stamps the executed notebook and then drops papermill's
`injected-parameters` cell, and both halves of that order are fixed: the stamper
cross-checks its parameter declaration against the cell, so it must run first, and
the cell must go before `jupytext --sync` propagates the argument values into the
paired `.py` - which for fx_pairs/06_linear once hardcoded a population hash into
source and sent a reader on a fresh registry into population.py:86.

So `outputs_digest` was computed over one more code cell than the file that gets
committed, and the recomputation at check time could never agree with it. Measured
on etfs/18_holdout_predictions, whose only override was the production-safe
REPLACE_HOLDOUT: inserting a single empty-output code cell reproduces the stored
digest exactly.

The cell is excluded from the digest, which now describes the notebook in the only
form anything reads it in. The notebook's own `parameters` cell stays covered: it
is source a reader edits, and dropping it would let a stamped notebook change what
it declares unnoticed.

* Displace the reduction fallback that kept crypto's cross-section at five names

Widening the crypto fixture to ten perpetuals fixed the price panel and not the
cross-section, so cs-crypto_perps_funding stayed red at 13_backtest with the same
refusal: "the predictions this sweep ranks carry 5 symbols against a price panel
of 19".

The panel 13_backtest loads is uncapped, so it went to ten. The predictions it
ranks come from 06_linear and 07_gbm, and those declared no reduction at all -
which does not mean they run unreduced. _collect_preview_reductions in
tests/pm_helpers.py injects `max_symbols: 5` when a notebook's mapping is empty,
because a preview run that reduces nothing is a canonical run wearing the wrong
tier. Both stages therefore kept fitting five names, and `top_k_grid [3, 5, 10]`
still had no member whose two disjoint legs fit: a long-short k drops when 2k
exceeds the tradeable count, which takes out k=3 at five names.

Declaring `PREVIEW_REDUCTIONS.max_symbols: 10` on 06_linear and 07_gbm displaces
the fallback at the fixture's full width. At ten names k=3 and k=5 both survive
(2k <= 10) and k=10 drops as it should, so the sweep has a realizable member.
08/09/10 get the same value: LABELS is not a reduction, so they were falling back
too. They skip in CI for want of a GPU, so the width only shows on a machine that
has one, which is where they would otherwise register a population narrower than
the fixture and than their own siblings. The sequence resolver takes max_symbols
directly and rejects only unknown keys, so it needs no companion fields.

The fixture's own registry is unaffected: generate_intermediates.py runs at
canonical tier with max_symbols 0, and its seeded artifacts are ten symbols wide.
