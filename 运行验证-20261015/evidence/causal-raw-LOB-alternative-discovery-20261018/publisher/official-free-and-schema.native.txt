L13: ## Why is order book essential?
L14: 
L15: Short-term and mid-term strategies are appreciated for higher returns and faster strategy validation compared to long-term trading. For those strategies, you need detailed market microstructure data including individual trades and order book.
L16: Order book data are needed for precise backtests, execution simulation, (statistical) arbitrage strategies or market making. Knowing the best price levels or available liquidity allows you to precisely determine for which prices are you able to trade, what liquidity is available in the order book or how much slippage will occur on trade. In the end, you are able to conduct precise backtests, that will closely match real execution.
L17: How do the order book data look like? Check out the cite2†data schemata and access .

L2: * * *
L3: 
L4: Available data types
L5: 
L6: Lake offers the following data types:
L7:   * trades – trades occurring on the given exchange aggregated by a single taker order and price.
L8:   * book – market depth (order book) snapshots in high frequency, at least once per 100ms depending on the exchange support. Contains 20 price levels for each order book side.
L9:   * candles – 1-minute OHLCV candles.
L10:   * level_1 – a practical derivate of book containing just the first price level on each order book side. book rows containing updates on deeper price levels are skipped, which makes this data type much faster to load and work with.
L11:   * book_delta_v2 – market depth (order book) updates in high frequency, supports unlimited (eg. 1000+) price levels on each order book side. Has even higher update frequency than book data, but is more complicated to process as you have to build order book model from the updates as shown in cite0†this interactive notebook†colab.research.google.com .
L12:   * book_1m – 1-minute order book snapshots containing 20 price levels on each order book side.
L13:   * deep_book_1m – 1-minute order book snapshots containing roughly one thousand price levels on each order book side.
L14:   * funding – funding and predicted funding rate plus mark_price for futures. On Binance for example this is updated every 3 seconds.
L15:   * open_interest – open interest for futures. On Binance for example this is updated every 20 seconds.
L16:   * liquidations – liquidation metrics such as side, price and quantity for futures. On Binance for example this is updated at most once per second.
L17: All data are partitioned by exchange, symbol and day and you can access any combination of those. Note that level_1 and candles data are just a derivates of book and trades data. Perpetuals/futures symbols have ‘-PERP’ suffix in their name.
L18: 
L19: You can find more details about exchange coverage and available history in the cite1†Coverage section.
L20: ## Access API
L21: 
L22: The data are available through an easy-to-use Python API. It offers high-performance parallelized data downloads, supports caching and downloading only new and unseen data once you add more time range or more token pairs to your query. This enables for example complex distributed machine-learning workloads.
L23:   * API source code: cite2†https://github.com/crypto-lake/lake-api†github.com L24:   * API reference documentation: cite3†https://lake-api.readthedocs.io†lake-api.readthedocs.io L25:   * API package on pypi: cite4†https://pypi.org/project/lakeapi/†pypi.org L26: For advanced users, it’s also possible to access the data directly through AWS S3. The data storage consists of a directory structure eg. `trades/exchange=BINANCE/symbol=BTC-USDT/dt=2022-01-01/random_name.parquet` and contains compressed parquet table files that are easy to load from any programming language. If you use this interface, please implement some kind of caching or don’t download the same data often to stay compliant with our Terms.
L27: Also be warned that the column names might slightly differ from the Python API and Schemata part of this page.
L28: Our affordable subscription plan For individuals has 300 GB soft download monthly limit. We also reserve the right to contact customers who scrape all data or misconfigure cache and cause unnecessary traffic in the scale of hundreds of gigabytes. More details can be found in the cite5†Terms of Service .

L30: 
L31: In all our data types, the origin_time column stands for the time when the event happened on the exchange, received_time is the time when the data was received and processed by our servers close to the exchange (mostly in AWS Tokyo zone).

L173: ### Notes
L174:   * All quantities, sizes and volumes are in the base asset (eg. BTC in case of BTC-USDT pair).
L175:   * All times are in nanosecond unix integer timestamp format
L176:   * All decimal numbers are as floats. This is to ensure good storage and computational performance. You may wish to round them to tick size and convert to Python Decimal or string to get the precise value eg. for a pretty human-readable representation.
L177:   * Order book data usually don’t contain origin_time. Dataframes with them may contain an empty origin_time column with 0 or -1.
L178:   * Data for the past day are uploaded every day between 00:00 UTC and 3:00 UTC.
